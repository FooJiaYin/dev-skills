# design

Every output is one static HTML file in the project's `docs/design/` (no interaction unless asked). Give the file path by default. Publish to an Artifact (one URL that stays the same across rounds) only in Remote Control mode (`$CLAUDE_CODE_BRIDGE_SESSION_ID` is set) or when the user asks for one. Speed matters: the first proposal page should exist within minutes, before any heavy building.

design picks directions, builds versions and keeps them as static HTML; refining and systematising code once a direction is set goes to impeccable commands ([references/impeccable.md](references/impeccable.md)). Never use impeccable's new-work, `live`, `generate` or `serve-question` — they need a server and are slow. If impeccable isn't installed, do those steps yourself and say so.

Versions that survive are the ones anchored in something real (the existing site, a saved reference, the brand, the meeting); versions built on an invented theme are the ones that get cut. Later versions go generic when they are made "to be different from v1" — so fix every direction before building, and never let one version see another.

The user describes feelings; directions need known style names, real images and concrete tokens, and finding them is your job, not the user's. Name styles from the [style library](references/styles/index.md) (saved guides and images, plus a CSV of named styles). Call every direction and every label by its known name — never an invented or poetic one.

1. **Collect what exists (fast).** Read the brief, meeting notes, spec, existing site, and `PRODUCT.md` / `DESIGN.md` if present — product facts belong in `PRODUCT.md`; `brief.md` keeps only this round's acceptance flows and brand rules; if `PRODUCT.md` is missing, offer impeccable `init`. Then pick the mode: a visual authority already exists (live site, `DESIGN.md`) and only part changes → **Block mode**; the ask is to unify or build a component library → **System mode**; otherwise → **Direction mode** (steps 2–7). Write the flows the meeting defined as acceptance criteria with their source; list the brand rules, including ones buried in chat logs. Save every reference image or URL the user gave into the project — a reference the agent can't open doesn't exist. If the user only says "it's ugly", check for bugs first (fonts not loading, styles duplicated). Ask only for what blocks the proposal; write it all to one shared `docs/design/brief.md`.
2. **Direction page (first deliverable).** Pick 2–4 style categories that fit the brief, then up to 8 named styles across them (or the ones the user named). For each, find 2–3 real examples yourself — screenshot real product sites with `headless-shots` into `docs/design/refs/`, link gallery shots. The page shows each style's name, images and one line on why it fits — no wireframe sketches. Mark your recommendation but don't list it first. Let the user pick (default 3), then write a style guide per [references/style-guide.md](references/style-guide.md) into `docs/design/` for each picked direction, with its side-by-side table in chat.
3. **Calibrate one screen.** Build one picked direction's key screen as a polished static mockup — real copy, real imagery, complete toolbars and states, at the finish of a mature product, and above impeccable's `reference/craft-floor.md` (quality floor and bans; resolve its absolute path as in [references/impeccable.md](references/impeccable.md) and give that path to every builder in step 4). Where craft-floor conflicts with the brief or the direction's style guide, the brief and guide win. Once the user accepts that bar, build the rest to it.
4. **Build in parallel.** One subagent per remaining direction, each given `brief.md` plus only its own guide and references. Same content (real copy, no lorem), same scope (key screen + 1–2 characteristic sections + shared chrome), same widths. Extend the calibrated direction to the same scope. Each names one peak moment. No subagent sees another version or earlier feedback. Temporary and QA output (check screenshots, temp pages) goes to the scratchpad, not the repo.
5. **Review before showing.** A fresh reviewer with no conversation history first checks every version against [references/review-checklist.md](references/review-checklist.md) — flow → usability basics → brand → peak moment → distinctness — with desktop and phone screenshots (`headless-shots` `steps.mjs`), without seeing detector output (it anchors judgment). Then run the impeccable `detect` CLI on each version, desktop and `--viewport 390x844` — it is not on PATH; resolve it as in [references/impeccable.md](references/impeccable.md); merge both and fix failures first. Deep review (`critique`) waits until step 7. If two versions read as siblings, rework the weaker one in a deliberately different direction.
6. **Show.** Put the versions on the same page in random order, labelled A, B, C…, plus a faithful replica of the current state if one exists. The page may be shown to a client, so keep it bare: one line of intro, then per version its style name and one line on the impression it gives. In chat, one table: version → reference → hypothesis → trade-off → peak moment, plus anything that departs from the spec or adds copy the source doesn't have. Don't pre-pick a favourite.
7. **Narrow.** Build a combination as a new version; keep the chosen ones and move the rest to `_archive/` (never delete). Run `impeccable critique` on the version the user leans to. After that, turn each reaction into its impeccable command ([table](references/impeccable.md)) and edit the code directly, with git as the rollback. To show the result, use the project's own server on a fixed port without auto-reload (check `lsof` for one already running); if there is no code yet, just give the HTML file path. Finish with `polish` → `harden` → `document` (writes `DESIGN.md`). Add each style the user confirmed that the library lacks to `skills/design/references/styles/` in the plugin's source repo, not the installed cache: guide (style-guide sections 1–3 and 5), index row, manifest entry — style only, nothing about the project. For full builds of several chosen versions, one shared brief, one agent per version, then a separate agent checks each against the brief.

**Block mode** (style already set, one block needs options). Put 3–4 options for that block side by side on one static page, labelled A–D with one plain line each. The page links the project's real CSS and tokens rather than imitating them; when publishing it as an Artifact, pass them via `files` or inline them. Generate each option along one of impeccable's direction words (bolder, quieter, distill, layout, typeset, colorize, animate, delight, overdrive) — the word is the lens, not the label. If a signature effect is wanted, this page is overdrive's proposal step; build the pick with `overdrive`. Review it like step 5 with only that block in scope, then port the chosen one into the code and continue as in step 7. With no code yet (prototype stage), all of this stays in `docs/design/` HTML.

**System mode** (unify into components or rules). `impeccable extract` (it first asks where the design system lives) → review the migrated surfaces like step 5, and grep the old pattern to confirm every use moved → `document` (it asks before overwriting `DESIGN.md`).

design reviews the rendered result; code quality belongs to `/code-review` in wrap-up.
