# design

Every output is HTML published to one Artifact URL that stays the same across rounds. Speed matters: the first proposal page should exist within minutes, before any heavy building.

Versions that survive are the ones anchored in something real (the existing site, a saved reference, the brand, the meeting); versions built on an invented theme are the ones that get cut. Later versions go generic when they are made "to be different from v1" — so fix every direction before building, and never let one version see another.

## Visual reference library

When a requested direction matches a saved style, consult the [visual reference library](references/styles/index.md), then open that style’s actual images and guide before designing. The library currently covers **dark glassmorphism**, **light minimalist with line icons**, and the user-referenced **Material Design / pastel modular** direction. Guides distinguish visible observations from suggested typography, border, radius, spacing, shadow and color tokens. Use them as optional references, not universal brand rules; the current brief and newly supplied images take precedence. Give each direction’s builder only its matching guide and images. Different directions should differ in composition and component treatment as well as palette.

1. **Collect what exists (fast).** Read the brief, meeting notes, spec and existing site. Write the flows the meeting defined as acceptance criteria with their source; list the brand rules, including ones buried in chat logs. Save every reference image or URL the user gave into the project — a reference the agent can't open doesn't exist. If the user only says "it's ugly", check for bugs first (fonts not loading, styles duplicated). Ask only for what blocks the proposal; write it all to one shared `brief.md`.
2. **Direction page (HTML, first deliverable).** Pick 2–4 style categories that fit the brief, then 8 direction cards across them. Each card: a known style name (not one you invented), one real reference site, palette swatches, a type sample, a mini layout sketch in CSS, what it borrows and what it deliberately doesn't, why it fits. Any two cards differ on at least 3 axes (layout, density, type, colour, motion, interaction model) — colour swaps don't count. Mark your recommendation but don't list it first. If `~/.claude/design-taste.json` exists, favour traits the user picked before and drop ones they rejected. Publish and let the user pick (default 3).
3. **Build previews in parallel.** One subagent per picked direction, each given `brief.md` plus only its own card. Same content (real copy, no lorem), same scope (first viewport + 1–2 characteristic sections + shared chrome), same widths. Each names one peak moment. Shared behaviour lives in one common file. No subagent sees another version or earlier feedback. Scratch output (screenshots, temp pages) goes to the scratchpad, not the repo.
4. **Review before showing.** A fresh reviewer with no conversation history checks every version against [references/review-checklist.md](references/review-checklist.md), in order: flow → usability → accessibility → brand → visual, with desktop and phone screenshots (`headless-shots` `steps.mjs`). Fix failures first. If two versions read as siblings, rework the weaker one in a deliberately different direction.
5. **Show.** Add the versions to the same Artifact in random order, plus one faithful replica of the current state as a baseline. One table: version → reference → hypothesis → trade-off → peak moment, plus anything that departs from the spec or adds copy the source doesn't have. Don't pre-pick a favourite.
6. **Narrow.** Build a combination as a new version; keep the chosen ones and move the rest to `_archive/` (never delete). Append to `~/.claude/design-taste.json` (create if missing): project, chosen and rejected directions, the user's reasons. For full builds of several chosen versions, one shared brief, one agent per version, then a separate agent checks each against the brief.
