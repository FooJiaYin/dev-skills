# design

Every output is one static HTML file in the project's `docs/design/` (no interaction unless asked). Give the file path by default. Publish to an Artifact (one URL that stays the same across rounds) only in Remote Control mode (`$CLAUDE_CODE_BRIDGE_SESSION_ID` is set) or when the user asks for one. Speed matters: the first proposal page should exist within minutes, before any heavy building.

Versions that survive are the ones anchored in something real (the existing site, a saved reference, the brand, the meeting); versions built on an invented theme are the ones that get cut. Later versions go generic when they are made "to be different from v1" — so fix every direction before building, and never let one version see another.

The user describes feelings; directions need known style names, real images and concrete tokens, and finding them is your job, not the user's. Name styles from the [style library](references/styles/index.md) (saved guides and images, plus a CSV of named styles). Call every direction and every label by its known name — never an invented or poetic one.

1. **Collect what exists (fast).** Read the brief, meeting notes, spec and existing site. Write the flows the meeting defined as acceptance criteria with their source; list the brand rules, including ones buried in chat logs. Save every reference image or URL the user gave into the project — a reference the agent can't open doesn't exist. If the user only says "it's ugly", check for bugs first (fonts not loading, styles duplicated). Ask only for what blocks the proposal; write it all to one shared `docs/design/brief.md`.
2. **Direction page (first deliverable).** Pick 2–4 style categories that fit the brief, then up to 8 named styles across them (or the ones the user named). For each, find 2–3 real examples yourself — screenshot real product sites with `headless-shots` into `docs/design/refs/`, link gallery shots. The page shows each style's name, images and one line on why it fits — no wireframe sketches. Mark your recommendation but don't list it first. If `~/.claude/design-taste.json` exists, favour traits the user picked before and drop ones they rejected. Let the user pick (default 3), then write a style guide per [references/style-guide.md](references/style-guide.md) into `docs/design/` for each picked direction, with its side-by-side table in chat.
3. **Calibrate one screen.** Build one picked direction's key screen as a polished static mockup — real copy, real imagery, complete toolbars and states, at the finish of a mature product. Once the user accepts that bar, build the rest to it.
4. **Build in parallel.** One subagent per remaining direction, each given `brief.md` plus only its own guide and references. Same content (real copy, no lorem), same scope (key screen + 1–2 characteristic sections + shared chrome), same widths. Extend the calibrated direction to the same scope. Each names one peak moment. No subagent sees another version or earlier feedback. Temporary and QA output (check screenshots, temp pages) goes to the scratchpad, not the repo.
5. **Review before showing.** A fresh reviewer with no conversation history checks every version against [references/review-checklist.md](references/review-checklist.md), in order: flow → usability → accessibility → brand → visual, with desktop and phone screenshots (`headless-shots` `steps.mjs`). Fix failures first. If two versions read as siblings, rework the weaker one in a deliberately different direction.
6. **Show.** Put the versions on the same page in random order, labelled A, B, C…, plus a faithful replica of the current state if one exists. The page may be shown to a client, so keep it bare: one line of intro, then per version its style name and one line on the impression it gives. In chat, one table: version → reference → hypothesis → trade-off → peak moment, plus anything that departs from the spec or adds copy the source doesn't have. Don't pre-pick a favourite.
7. **Narrow.** Build a combination as a new version; keep the chosen ones and move the rest to `_archive/` (never delete). Append to `~/.claude/design-taste.json` (create if missing): project, chosen and rejected directions, the user's reasons. Add each style the user confirmed that the library lacks to `skills/design/references/styles/` in the plugin's source repo, not the installed cache: guide (style-guide sections 1–3 and 5), index row, manifest entry — style only, nothing about the project. For full builds of several chosen versions, one shared brief, one agent per version, then a separate agent checks each against the brief.
